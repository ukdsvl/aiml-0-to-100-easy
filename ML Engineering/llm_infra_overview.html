Overview

Large Language Model (LLM) and Vision-Language Model (VLM) inference has evolved from simple single-GPU Python scripts into highly distributed, low-latency infrastructure engineering systems. Serving billion-parameter models at scale requires overcoming strict memory bottlenecks, high arithmetic intensity imbalances, and fluctuating request workloads.

This technical reference document synthesizes foundational inference concepts, memory optimization techniques, distributed serving engines, hardware economic divergences, and production-grade architectures.

+-----------------------------------------------------------------------------------+
|                        Traditional vs. Optimized Inference                        |
|                                                                                   |
| Standard PyTorch  ---> [ Unbounded KV-Cache ] ---> [ Sequential GPU Memory Stalls ]|
| vLLM / Dynamo     ---> [ PagedAttention     ] ---> [ Zero-Copy Memory Management ]|
| Ray Serve / Cloud ---> [ Distributed Workers ] ---> [ Elastic Autoscaling Pool  ] |

Part 1: Foundations of LLM Inference Engineering

LLM inference is fundamentally divided into two distinct computational phases: Prefill and Decoding. Understanding their hardware profiles is essential for building scalable serving architectures.

The Two-Phase Inference Lifecycle

  1. Prefill Phase (Matrix-Multiply Bound):
    • Processes the entire input prompt in parallel across GPU tensor cores.
    • Exhibits high arithmetic intensity and high computational throughput.
    • Allocates the initial Key-Value (KV) cache tensors for all prompt tokens.
  2. Decoding Phase (Memory-Bandwidth Bound):
    • Generates output tokens auto-regressively one token at a time ($O(N)$ sequential loops).
    • Exhibits low arithmetic intensity because weights and KV-cache blocks must be fetched from High Bandwidth Memory (HBM) to SRAM for every single generated token.
    • Bounded strictly by GPU memory bandwidth (e.g., NVIDIA H100/H200 HBM transfer rates) rather than floating-point performance (TFLOPS).

Computational Complexity & KV-Cache Footprint

For a transformer model with hidden dimension $D$, $L$ layers, $H$ attention heads, and sequence length $S$, the KV cache memory required per sequence in FP16 precision is:

\[\text{Memory}_{\text{KV}} = 2 \cdot \text{Layers} \cdot \text{SeqLen} \cdot \text{HiddenDim} \cdot \text{BytesPerParam}\]

Without intelligent memory virtualization, naive contiguous memory allocation leads to massive internal fragmentation, wasting up to $60\% - 80\%$ of allocated GPU VRAM due to pre-allocated maximum sequence lengths.

Part 2: Core Serving Engines & Memory Optimization

Modern inference engines like vLLM, AirLLM, and NVIDIA Dynamo implement architectural innovations to eliminate memory waste and maximize GPU utilization.

PagedAttention & Memory Virtualization

Inspired by virtual memory paging in operating systems, PagedAttention partitions the KV cache of each sequence into fixed-size blocks (e.g., 16 tokens per block).

Logical KV Cache (Contiguous to Model):
[ Token 1 .. Token 16 ] -> [ Token 17 .. Token 32 ] -> [ Token 33 .. Token 48 ]

Physical GPU VRAM Blocks (Non-Contiguous Paging):
[ Block #42 ] <---> [ Block #105 ] <---> [ Block #12 ]
  • Zero Internal Fragmentation: Blocks are allocated dynamically on-demand as tokens are generated.
  • Efficient Memory Sharing: Enables prefix sharing and beam search branching without duplicating underlying tensor data in VRAM.

Extreme Low-Memory Inference (AirLLM)

For developers running massive models (e.g., 70B+ parameters) on consumer-grade hardware with limited VRAM (e.g., a single 24GB RTX 3090/4090), AirLLM bypasses standard memory limits by streaming model layers dynamically from system RAM to GPU VRAM layer-by-layer during execution:

\[\text{Latency}_{\text{AirLLM}} = \sum_{l=1}^{L} \left( \text{TransferTime}(\text{Layer}_l) + \text{ComputeTime}(\text{Layer}_l) \right)\]

While sacrificing token generation speed (Tokens/sec), AirLLM enables local execution of frontier-scale models on standard desktop hardware.

Part 3: Distributed Serving Architectures & Ray Serve

Scaling inference across multiple nodes requires distributed orchestration frameworks like Ray Serve, which decouples HTTP routing, request batching, and model execution worker pools.

Distributed Ray Serve Pipeline 

Client Request ---> [ Ray Serve HTTP Ingress Gateway ]
                                  |
            +---------------------+---------------------+
            |                     |                     |
            v                     v                     v
     [ Worker Node 1 ]     [ Worker Node 2 ]     [ Worker Node 3 ]
     (vLLM Replica A)      (vLLM Replica B)      (vLLM Replica C)

Key Distributed Primitives

  • Dynamic Autoscaling: Automatically spins up or scales down GPU replica pods based on incoming request queue depth and P99 latency SLAs.
  • Continuous Batching (In-Flight Batching): Dynamically inserts new incoming requests into ongoing decoding batches as completed sequences finish, eliminating idle GPU compute bubbles.

Part 4: Production-Ready VLM Stacks (Pinterest & NVIDIA Dynamo)

Vision-Language Models (VLMs) introduce multimodal tokenization overhead, combining image patch embeddings with text sequences.

Pinterest VLM Serving Stack on NVIDIA Dynamo

Pinterest engineering constructed an optimized VLM serving stack leveraging NVIDIA Dynamo to handle high-throughput visual search and recommendation payloads:

  1. Vision Encoder Offloading: Image patches are pre-processed and encoded asynchronously on dedicated accelerator pipelines before entering the autoregressive transformer backbone.
  2. Dynamic Tensor Parallelism: Automatically shards multi-modal projection layers across NVLink-connected GPUs to minimize inter-node communication latency during multimodal prefill phases.

Part 5: Hardware Economics & Infrastructure Divergence

The economics of AI infrastructure have experienced a fundamental divergence between training and inference clusters.

Training vs. Inference Economic Matrix

Dimension Training Infrastructure Inference Infrastructure
Primary Bottleneck Inter-node network bandwidth (InfiniBand, NVLink) HBM memory bandwidth & capacity
Utilization Profile Sustained high compute utilization ($>85\%$ FLOPs) Variable, bursty, batch-size dependent
Precision Format FP8 / BF16 mixed-precision checkpoint updates INT8 / FP8 / INT4 quantized execution
Cost Driver Capital expenditure (CapEx) on massive GPU clusters Operational expenditure (OpEx) & query cost

Part 6: AWS & Enterprise Production Deployments

Enterprise deployments on cloud providers (such as AWS Amazon SageMaker HyperPod and Amazon Bedrock) integrate automated failover and capacity-aware scaling.

Capacity-Aware Inference & Automatic Instance Fallback

Production systems maintain strict service-level agreements (SLAs) by implementing Capacity-Aware Routing:

Incoming Request ---> [ Primary SageMaker Endpoint (H100) ]
                                    |
                        [ Capacity Check / Health ]
                                    |
                    +---------------+---------------+
                    | (Healthy)                     | (Degraded / OOM)
                    v                               v
         [ Execute on Primary ]          [ Automatic Fallback to Secondary (A10G) ]

Limitations and Open Questions

  1. KV Cache Memory Pressure under Infinite Context: Supporting $128\text{k}+$ token context windows consumes significant VRAM per concurrent stream, limiting maximum batch sizes.
  2. Quantization Degradation: Aggressive quantization (e.g., INT4 / GPTQ / AWQ) can introduce subtle accuracy drift in complex reasoning and tool-calling agent tasks.
  3. Multi-Modal Latency Imbalance: Vision encoder latency varies significantly based on image resolution, complicating predictable SLA enforcement in real-time VLM pipelines.

Final Technical Takeaways

  1. Memory Bandwidth Dominance: Decoding is strictly memory-bandwidth bound; optimization relies on paged memory virtualization (PagedAttention) and aggressive quantization.
  2. Prefill vs. Decode Separation: Modern serving engines decouple compute-bound prefill from memory-bound decoding to maximize hardware utilization.
  3. Distributed Orchestration: Tools like Ray Serve and vLLM are essential for maintaining sub-second P99 latencies under bursty production workloads.
  4. Economic Divergence: Inference infrastructure prioritizes cost-per-query, HBM bandwidth, and operational stability over massive inter-node training fabrics.
