Decision Models & Joint Energy Value (JEV) Architectures: Comprehensive Technical Reference Guide

Primary references

  • vLLM - High-Throughput Serving for Prefill-Only Decision Models
  • AnyJev GitHub Repository - Calibrated Energy-Based Classifier Architectures
  • SearchJEV: System-1 Calibrated Models for Search Agents (arXiv:2610.05107)

Source and verification note

The architectural concepts, Jev-style decision interface, AnyJev readouts, calibration results, and SearchJev claims below are supported by the linked primary sources. vllm-sr

Some quantitative claims in the later benchmark, latency, cost, calibration-comparison, and production case-study sections are presented as illustrative engineering estimates rather than results reproduced from the primary sources. Treat those figures as examples of how to evaluate a decision-model deployment, not as universally verified benchmarks.

Overview

Generative large language models (LLMs) operate through autoregressive next-token generation, producing output one token at a time. For deterministic classification, multi-class routing, entity extraction, and structured action selection, this sequential decoding can introduce avoidable latency, memory overhead, and unreliable confidence.

Decision models shift this workload away from generative autoregression toward prefill-only, Joint Energy Value (JEV), and energy-based model (EBM) architectures. Instead of generating a label as text, the model scores a supplied candidate set and returns a probability distribution over the candidates.

The core decision pattern is:

[ \text{State} + \text{Question} + \text{Candidate Set} \rightarrow \text{Typed probability distribution} ]

Decision 1.0 expresses this as state + questions + criteria → typed probability distributions, where the application defines the allowed choices and the model evaluates them. vllm-sr

+-----------------------------------------------------------------------------------+
|                        Generative Auto-Regressive Paradigm                        |
|                                                                                   |
| Input Prompt -> [ Encoder Prefill ] -> [ Token 1 ] -> [ Token 2 ] ... [ END ]     |
|                                        (Sequential O(N) generation loops)         |
|                                                                                   |
| Latency: High (100 ms - 2,000 ms)                                                 |
| Memory: KV-cache bound                                                            |
| Calibration: Often poor without additional work                                   |
+-----------------------------------------------------------------------------------+

                                       VS

+-----------------------------------------------------------------------------------+
|                           Decision Model (JEV) Paradigm                           |
|                                                                                   |
| Input Prompt + Candidate Set -> [ Prefill Encoder ] -> [ Joint Energy Head ]      |
|                                                          (Single forward pass)    |
|                                                                                   |
| Latency: Low, especially for short contexts                                       |
| Memory: No generated-token KV-cache growth                                        |
| Calibration: Designed for typed probability outputs                               |
+-----------------------------------------------------------------------------------+

The latency, memory, and calibration characteristics shown above are conceptual representations of the two paradigms. Actual results depend on model size, sequence length, batch size, hardware, serving engine, and candidate-set size.

Part 1: Foundations of Decision Models vs. Generative LLMs

Traditional generative LLMs often evaluate class probabilities by predicting text tokens, such as generating "Yes", "No", or a JSON object. This introduces engineering and statistical challenges in production systems:

  • The model may emit malformed JSON or an invalid class name.
  • The output must be parsed and validated.
  • Label order can affect next-token logits.
  • Confidence from generated text is often poorly calibrated.
  • Each generated token adds sequential decoding work.

By contrast, a decision model receives the candidate options directly and scores them in context. Decision 1.0 evaluates each supplied candidate against the evidence and question, returning probabilities rather than generated text. vllm-sr

Computational and architectural comparison

Dimension Generative autoregressive LLMs Prefill-only / decision models (JEV)
Decoding complexity (O(N)) sequential autoregressive loops (O(1)) single-pass parallel prefill
Typical inference latency Tens to thousands of milliseconds Low, especially for short contexts
KV-cache memory overhead Grows with generated sequence length No generated-token KV-cache growth
Probabilistic calibration Often overconfident without calibration work Designed for typed probability outputs
Generative hallucination Possible syntax errors or invalid classes Hard-bounded candidate scoring
Throughput bottleneck Often memory-bandwidth bound during decoding Compute-bound tensor operations during prefill
Serving framework Autoregressive vLLM, TensorRT-LLM, PagedAttention Prefill-optimized runners, including vLLM and llama.cpp

The exact latency and throughput depend on the model, context length, batch size, and hardware. The important structural distinction is that decision models avoid generating decision text token by token. vllm-sr

Computational complexity and FLOP breakdown

For a sequence length (L), hidden dimension (D), and (M) transformer layers, an autoregressive model generating (T) output tokens requires floating-point operations that scale approximately as:

[ \text{FLOPs}_{\text{generative}} \approx 2 \cdot M \cdot (L \cdot D^2 + T \cdot L \cdot D + T \cdot D^2) ]

A prefill-only decision model evaluates the target decision directly over the input sequence without generating additional text, so (T = 0). The approximate FLOP count reduces to:

[ \text{FLOPs}_{\text{decision}} \approx 2 \cdot M \cdot L \cdot D^2 ]

This is a simplified approximation. It highlights the main source of savings—removing generated tokens—but does not capture all implementation-specific costs, such as attention overhead, candidate scoring, batching, and memory movement.

By removing token-generation loops, serving engines avoid repeated memory-bandwidth work associated with decoding each new token. SearchJev reports that its decision model achieves 5.2 to 5.3 times faster decisions than same-size Qwen3.5 autoregressive models on SearchDecision-Bench. arxiv

Part 2: Joint Energy Value (JEV) Mathematical Formulation

Joint Energy Value (JEV) frameworks ground classification and structured decision-making in energy-based model (EBM) theory. Instead of directly modeling a conditional probability distribution (P(Y \mid X)) with a simple linear classification head over context (X), a JEV model assigns a scalar energy (E(X, Y)) to the joint space of input context (X) and candidate action or class (Y).

User Context (X) ----+
                     +---> [ Joint Energy Model E(X, Y) ] ---> Scalar Energy E_i
Candidate Class (Y_i)-+

JEV probability derivation

Let (X \in \mathcal{X}) be the input feature space, such as a query, user profile, or document context. Let (Y \in \mathcal{Y} = {y_1, y_2, \ldots, y_C}) be the set of (C) candidate decisions.

The joint probability density (P(X, Y)) can be parameterized using a Gibbs-Boltzmann distribution:

[ P(X, Y) = \frac{\exp\left( -E(X, Y) / T \right)}{Z} ]

where:

  • (E(X, Y)) is the joint energy of context (X) and candidate (Y).
  • (T) is a temperature parameter.
  • (Z) is the partition function.

The partition function integrates over the configuration space:

[ Z = \sum_{y’ \in \mathcal{Y}} \int_{\mathcal{X}} \exp\left( -E(x’, y’) / T \right) \, dx’ ]

By marginalizing over (X), the conditional class probability (P(Y = y_i \mid X)) cancels the intractable partition function:

[ P(Y = y_i \mid X) = \frac{P(X, Y = y_i)} {\sum_{j=1}^{C} P(X, Y = y_j)} = \frac{\exp\left( -E(X, y_i) / T \right)} {\sum_{j=1}^{C} \exp\left( -E(X, y_j) / T \right)} ]

In practice, the model computes energies or logits for the supplied candidates and normalizes them over that candidate set. Decision 1.0 follows this general pattern: it scores the candidates provided in the request and returns their probabilities. vllm-sr

Unconditional marginal energy and OOD detection

The marginal energy (E(X)) of input context (X) is obtained by aggregating energy over all candidate decisions:

[ E(X) = -T \cdot \log \sum_{y \in \mathcal{Y}} \exp\left( \frac{-E(X, y)}{T} \right) ]

This marginal energy can be used as an explicit signal for out-of-distribution (OOD) detection, intent validation, and retrieval-quality checks.

                 Unconditional Marginal Energy E(X)
                                  |
          +-----------------------+-----------------------+
          |                                               |
   Low marginal energy                            High marginal energy
   E(X) < threshold                               E(X) > threshold
          |                                               |
          v                                               v
[ In-distribution query ]                     [ Out-of-distribution query ]
[ Proceed to decision ]                       [ Fallback / rejection mode ]

Interpretation:

  • Low marginal energy: the input is relatively well supported by the candidate space.
  • High marginal energy: the input may not match any valid candidate, suggesting an OOD input, unsupported context, or invalid request.

This is a useful design pattern, but it requires empirical threshold selection on representative validation data. A high-energy input is not automatically a hallucination; it may simply be a valid request outside the trained candidate distribution.

Part 3: AnyJev, SearchJEV, and Specialized Decision Architectures

Modern open-weight decision models adopt different architectural approaches depending on deployment constraints, such as e-commerce search, named-entity recognition, RAG routing, and agent action selection.

                              Decision Model Variants
                                         |
        +--------------------------------+--------------------------------+
        |                                |                                |
 [ AnyJev Architecture ]       [ SearchJEV Architecture ]      [ GLiNER 2.5 / GLIDE ]
 - Universal decision readout  - Search-state decisions        - Entity extraction
 - Rotation-based L0 readout   - Dual-system search agents     - Reasoning decision model
 - Self-distilled Tacit models - Calibrated confidence         - Structured extraction

AnyJev: universal decision readout

AnyJev turns an LLM into a Jev-style decision model. It returns typed decisions and probabilities over supplied options without parsing generated text. github

AnyJev provides two paths:

Path Training requirement Mechanism
Training-free Decider No training, no labels Reads typed decisions from any open causal LLM
Self-distilled Tacit Uses Tacit checkpoints One forward pass per decision, with optional adaptive reasoning escalation

A raw next-token logit readout can change its answer when options are reordered and can carry a preference for particular label strings. AnyJev’s L0 readout averages position bias over rotations of the options and divides out the label prior. github

A conceptual energy-style formulation for a candidate (y_i) is:

[ E(X, Y = y_i) = -\mathbf{w}_{y_i}^{T} \cdot \text{Pooling}\left( \text{Transformer}\left([X ; y_i]\right) \right) ]

where:

  • (X) is the input state.
  • (y_i) is a candidate option.
  • (\mathbf{w}_{y_i}) is a learnable projection vector for that candidate.
  • (\text{Pooling}) produces a fixed-size representation from the transformer output.

This equation is an illustrative formulation of a pooled candidate-scoring head. It is not a claim that every AnyJev implementation uses this exact parameterization.

SearchJEV: low-latency search decisions

SearchJev is a fast, calibrated System-1 model for search agents. It separates short search decisions from System-2 reasoning and generation. Given a search state and a decision schema, SearchJev directly scores legal options without autoregressive output generation. arxiv

A conceptual two-tower formulation for query-product scoring is:

[ E(\text{Query}, \text{Product}_i) = -\left( \phi(\text{Query})^{T} \psi(\text{Product}_i) \right)

  • b_i ]

where:

  • (\phi) is a query encoder.
  • (\psi) is a product encoder.
  • (b_i) is an item-specific bias term, potentially reflecting popularity or prior click-through rate.
Query context ---> [ Query encoder phi ] ---> Vector u \
                                                        +--> Dot product + bias ---> E(Q, P_i)
Product data  ---> [ Product encoder psi ] ---> Vector v /

This two-tower structure is a common retrieval and reranking design. SearchJev’s published contribution is specifically its use of Soft-Label Learning for Calibrated Decisions (SLCD), its SearchDecision-Bench benchmark, and its dual-system search-agent evaluation. arxiv

Contrastive learning for decision models

Contrastive Language Models for decisions, such as Contrastive-LM/CLM-v0.1-8B, can use InfoNCE-style losses over joint energy states. Positive query-decision pairs are pushed toward lower energy, while negative candidates receive higher energy.

[ \mathcal{L}{\text{InfoNCE}} = -\log \frac{ \exp\left( -E(X, Y^+) / T \right) }{ \exp\left( -E(X, Y^+) / T \right) + \sum{j=1}^{K} \exp\left( -E(X, Y_j^-) / T \right) } ]

where:

  • (Y^+) is the positive candidate.
  • (Y_j^-) are negative candidates.
  • (K) is the number of negatives.
  • (T) is a temperature parameter.

This is a standard contrastive-learning formulation added for technical context. The exact loss used by a particular CLM implementation should be verified against its repository and model card.

Part 4: Probabilistic Calibration and Overconfidence Analysis

A common failure mode of autoregressive LLM classifiers is overconfidence: assigning very high softmax probability to incorrect predictions. Decision models address this by making calibrated probability outputs a first-class part of the interface.

Expected Calibration Error

Expected Calibration Error (ECE) measures the alignment between predicted confidence (\hat{p}) and observed accuracy across (B) confidence bins (I_b):

[ \text{ECE} = \sum_{b=1}^{B} \frac{|I_b|}{N} \left| \text{acc}(I_b) - \text{conf}(I_b) \right| ]

where:

  • (N) is the total number of predictions.
  • (I_b) is a confidence bin.
  • (\text{acc}(I_b)) is observed accuracy within the bin.
  • (\text{conf}(I_b)) is average predicted confidence within the bin.

[ \text{acc}(I_b) = \frac{1}{|I_b|} \sum_{i \in I_b} \mathbb{I}(\hat{y}i = y_i), \qquad \text{conf}(I_b) = \frac{1}{|I_b|} \sum{i \in I_b} \hat{p}_i ]

Lower ECE indicates better calibration.

Perfect calibration (ECE = 0.0)          Overconfident model (high ECE)

Accuracy                                  Accuracy
 1.0 |         /                           1.0 |         /
     |        /                                |        /  . (Actual accuracy)
 0.5 |       /                             0.5 |       / .
     |      /                                  |      /.    <-- Large gap
 0.0 +------------                          0.0 +------------
     0.0   0.5   1.0 Confidence                0.0   0.5   1.0 Confidence

AnyJev reports the following comparison for Qwen3-8B on a 20-way BANKING77 task with 300 test items. github

Part 5: Serving Infrastructure and Prefill-Only Optimizations

Because decision models eliminate autoregressive decoding loops, traditional serving configurations can allocate KV-cache memory that is never used for generated tokens.

Standard vLLM pipeline:
Input -> [ Prefill phase ] -> [ Allocate KV-cache ] -> [ Decode loop steps 1..N ]
                                                          (Unnecessary for decision models)

Prefill-only vLLM-SR / llama.cpp serving pipeline:
Input -> [ Parallel prefill compute ] -> [ Energy scoring head ] -> Return result
                                                          (Single pass)

Serving optimization strategies

  • Avoid unnecessary KV-cache allocation. For prefill-only decision workloads, configure the serving engine to avoid retaining KV-cache state for generated tokens that will never be produced.
  • Use dynamic tensor-core batching. Group many classification requests into large parallel prefill matrix multiplications.
  • Quantize for edge deployment. GGUF quantized models, such as Q4_K_M or Q8_0, can run through llama.cpp on CPU or edge hardware, subject to accuracy and latency validation.
  • Batch independent questions. Decision 1.0’s Kai and Lex native Python API accepts up to 128 independent requests and 512 total decisions per local SDK batch submission. The runtime groups work into physical batches; 512 describes submission capacity, not simultaneous forward passes or measured throughput. vllm-sr
  • Separate candidate scoring from generation. Score all candidates for a question in a single forward pass where the architecture supports it, as Decision 1.0’s Lux model does. vllm-sr

A simplified batched scoring operation is:

[ \mathbf{Y}{\text{logits}} = \mathbf{X}{\text{prefill embeddings}} \cdot \mathbf{W}_{\text{energy head}}^{T} ]

where:

  • (\mathbf{X}_{\text{prefill embeddings}}) contains pooled prefill representations.
  • (\mathbf{W}_{\text{energy head}}) contains candidate projection weights.
  • (\mathbf{Y}_{\text{logits}}) contains raw scores for each candidate.

Actual serving performance requires measuring p50, p95, and p99 latency under realistic batch sizes and context lengths.

Part 6: Training and Fine-Tuning Decision Models with Unsloth and TRL

Fine-tuning a decoder model, such as Llama-3.2-1B or Qwen-2.5-0.5B, into a decision model generally involves replacing standard causal language-modeling loss with supervised classification loss over pooled hidden states or candidate energy scores.

Input sequence [X]
        |
        v
[ Llama / Qwen backbone ]
        |
        v
[ Pooled last-token hidden state ]
        |
        v
[ Energy projection layer ]
        |
        v
Cross-entropy loss versus target label

This is a supervised classification approach. It differs from AnyJev’s self-distillation approach, in which a Tacit model learns to produce in one forward pass the answers it reaches when it reasons, without human labels or a separate teacher model. github

Fine-tuning pipeline with Unsloth and PyTorch

The following script is an illustrative implementation. It loads a lightweight base backbone, attaches a classification head, and fine-tunes it with Unsloth. It is not copied from the official Unsloth or Liquid4All decision-model notebooks and should be adapted to the target data schema and model.

import torch
from torch import nn
from unsloth import FastLanguageModel
from transformers import Trainer, TrainingArguments
from datasets import Dataset

# 1. Configuration and model loading
max_seq_length = 2048
dtype = None  # Auto-detect Float16 or BFloat16
load_in_4bit = True

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="unsloth/Llama-3.2-1B-Instruct",
    max_seq_length=max_seq_length,
    dtype=dtype,
    load_in_4bit=load_in_4bit,
)

# 2. Add LoRA adapters
model = FastLanguageModel.get_peft_model(
    model,
    r=16,
    target_modules=[
        "q_proj", "k_proj", "v_proj", "o_proj",
        "gate_proj", "up_proj", "down_proj",
    ],
    lora_alpha=16,
    lora_dropout=0,
    bias="none",
    use_gradient_checkpointing="unsloth",
    random_state=3407,
)

# 3. Define a custom decision head wrapper
class JEVDecisionModel(nn.Module):
    def __init__(self, base_model, num_classes, hidden_dim):
        super().__init__()
        self.base_model = base_model
        self.energy_head = nn.Linear(hidden_dim, num_classes, bias=False)

    def forward(self, input_ids, attention_mask, labels=None):
        outputs = self.base_model(
            input_ids=input_ids,
            attention_mask=attention_mask,
            output_hidden_states=True,
        )

        # Use the final-token representation as the pooled decision state.
        last_hidden_state = outputs.hidden_states[-1][:, -1, :]

        # Treat logits as negative energies: E(X, Y) = -logits.
        logits = self.energy_head(last_hidden_state)

        loss = None
        if labels is not None:
            loss_fct = nn.CrossEntropyLoss()
            loss = loss_fct(logits, labels)

        return {"loss": loss, "logits": logits}

# 4. Prepare a small illustrative dataset
train_data = {
    "text": [
        "Category: Electronics | Query: Wireless noise canceling headphones",
        "Category: Clothing | Query: Cotton summer t-shirt blue",
        "Category: Books | Query: Introduction to quantum computing algorithm",
    ],
    "label": [0, 1, 2],  # 0: Electronics, 1: Clothing, 2: Books
}

def tokenize_function(examples):
    tokens = tokenizer(
        examples["text"],
        padding="max_length",
        max_length=128,
        truncation=True,
    )
    tokens["labels"] = examples["label"]
    return tokens

dataset = Dataset.from_dict(train_data)
tokenized_dataset = dataset.map(tokenize_function, batched=True)

# 5. Configure training
training_args = TrainingArguments(
    output_dir="./jev_decision_model_checkpoints",
    per_device_train_batch_size=4,
    gradient_accumulation_steps=2,
    warmup_steps=5,
    max_steps=30,
    learning_rate=2e-4,
    fp16=not torch.cuda.is_bf16_supported(),
    bf16=torch.cuda.is_bf16_supported(),
    logging_steps=1,
    optim="adamw_8bit",
    weight_decay=0.01,
    lr_scheduler_type="linear",
    seed=3407,
)

# 6. Instantiate the wrapper and trainer
wrapped_model = JEVDecisionModel(
    base_model=model,
    num_classes=3,
    hidden_dim=model.config.hidden_size,
)

trainer = Trainer(
    model=wrapped_model,
    args=training_args,
    train_dataset=tokenized_dataset,
)

# 7. Train
trainer.train()

For production training, use a sufficiently large and representative labeled dataset, reserve a held-out validation split, and evaluate accuracy, calibration, latency, and escalation behavior—not training loss alone.

Limitations and Open Questions

Dynamic candidate spaces

Standard JEV-style models require a predefined candidate set (\mathcal{Y}). Evaluating millions of dynamic candidates in a single pass is usually impractical.

A common hybrid approach is:

Large candidate universe
        |
        v
[ Bi-encoder / vector search prefilter ]
        |
        v
[ Top-K candidate set ]
        |
        v
[ Decision model scores top-K candidates ]
        |
        v
[ Typed probability distribution ]

This combines the recall of vector search with the calibrated scoring of a decision model.

Context-window scaling

Prefill-only execution removes autoregressive decoding, but it does not remove the cost of processing a long input. For very long contexts, attention can still incur substantial compute and memory cost during the initial prefill phase.

For standard full attention, prefill attention cost scales approximately as:

[ O(L^2) ]

where (L) is the sequence length. Hybrid architectures, sparse attention, sliding-window attention, and efficient sequence mixers can reduce this cost, but their effectiveness depends on the workload.

Multi-step reasoning

Complex mathematical logic, multi-step planning, and chain-of-thought reasoning cannot always be compressed into a single-pass prefill. Hybrid “thinking” decision models, such as Fastino GLIDE, are one approach to combining fast decision readouts with selective reasoning.

AnyJev takes a related approach with adaptive escalation: low-confidence Tacit decisions can be sent to the model’s own reasoning, subject to a configured cap. At the default settings, at most 20% of the last 1,000 decisions escalate, and each escalated decision has a reasoning budget of 8,192 tokens. github

Final Technical Takeaways

  • Paradigm shift: Decision models eliminate sequential token-generation loops for structured decisions, scoring supplied candidates through a prefill-oriented decision path.
  • Efficiency: Removing generated-token decoding avoids KV-cache growth during decision generation and can substantially reduce latency; SearchJev reports 5.2 to 5.3 times faster decisions than same-size autoregressive models on its benchmark. arxiv
  • Calibration: JEV-style probability outputs make confidence usable for policy thresholds. AnyJev’s L0 readout reduces ECE from 0.240 to 0.184 and increases the share of decisions automatable at 5% error or less from 7.7% to 46.3% without labels. github
  • OOD safety: Marginal energy (E(X)) provides a mathematical signal for detecting unsupported inputs, invalid agent tool calls, and out-of-distribution queries, subject to empirical threshold calibration.
  • Main trade-off: Single-pass decision models are fast and inexpensive, but derivation-heavy tasks still require System-2 reasoning, planning, or human escalation. arxiv
  • Engineering implication: Use decision models as a programmable control layer between understanding and action: define candidate sets explicitly, return calibrated distributions, automate only within validated confidence thresholds, and escalate uncertain or high-impact cases. vllm-sr
