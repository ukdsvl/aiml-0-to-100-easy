Decision Models: Jev, AnyJev, and the Decision Layer for AI Systems

Reference: Introducing Decision 1.0: Open Decision Foundation Models

Decision models are a new class of language models optimized to make fast, typed, probability-bearing decisions rather than generate free-form text. They sit between an application’s understanding of a request and its next action: given a state, a question, and candidate options, they return calibrated distributions over those options.

The central pattern is:

\[\text{State} + \text{Questions} + \text{Criteria} \rightarrow \text{Typed probability distributions}\]

This document covers the Jev-style decision-model interface, the architecture and trade-offs of open decision models, the AnyJev training-free and self-distilled approaches, calibration, deployment, and practical use in agents, search, routing, and evaluation.

Part 1: Foundations

What is a decision model?

A decision model is a model that consumes a context or state and returns a structured decision over a predefined set of alternatives. Instead of producing a paragraph of reasoning or a natural-language answer, it scores candidates and returns probabilities.

A typical decision request contains:

  • State: the evidence or context to evaluate, such as a support ticket, document, agent trace, search result, or user request.
  • Question: what the system needs to determine.
  • Candidates or criteria: the allowed answers, actions, labels, or rubric levels.
  • Output: a selected option plus a probability distribution over all options.

For example, given a customer message about a duplicate charge, a decision model may answer:

  • Which team should handle this: billing, technical, or sales?
  • Did the customer request a refund?
  • How urgent is the issue: can wait, this week, or today?

The model returns a distribution such as billing: 0.91, technical: 0.07, sales: 0.02, allowing the application to route the request, set an escalation threshold, or prioritize a queue. vllm-sr

Why not just use an LLM?

A generative LLM can perform classification by prompting it to output a label. However, for high-volume operational decisions, this approach has several drawbacks:

Concern Generative LLM classification Decision model
Output format Text that may need parsing or validation Typed decision with option probabilities
Latency Often requires autoregressive generation Can score candidates in one forward pass
Cost Higher when generating reasoning tokens Lower when decisions are read from logits or a single prefill
Confidence Often poorly calibrated without extra work Designed to expose probabilities for policy decisions
Flexibility Broad reasoning and generation capability Focused on choosing among supplied alternatives
Best fit Open-ended reasoning, planning, writing Routing, gating, triage, scoring, policy checks

Decision models do not replace LLMs. They separate the frequent, short-horizon decisions that an application must make from the slower System-2 work of planning, reasoning, query generation, and answer composition. arxiv

System 1 versus System 2

The terminology comes from a dual-process view of cognition:

  • System 1 is fast, automatic, and low-effort. In AI systems, this maps to immediate decisions such as “route this ticket,” “is this relevant?”, or “should this action be allowed?”
  • System 2 is slower, deliberate, and effortful. In AI systems, this maps to multi-step planning, tool use, complex reasoning, and generating a final answer.

SearchJev explicitly applies this split to search agents: a small decision model handles repeated short decisions about relevance, evidence sufficiency, and search actions, while a larger System-2 model handles planning, query generation, and answer composition. arxiv

User request

     v
+---------------------+
| System 1: Decision  |  Fast, typed, probabilistic
| - relevance?        |
| - enough evidence?  |
| - next action?      |
+---------------------+

Part 2: The Jev Decision Interface

Three decision types

The Jev-style interface defines three primary decision types. Decision 1.0 uses the names Choice, Noul, and Score. vllm-sr

Type Question form Output Typical use
Choice “Which option is best?” One selected candidate and a distribution over candidates Routing, action selection, classification
Noul “Is this condition true?” Probability of yes Policy gates, evidence checks, escalation
Score “Rate this on an ordered rubric.” Distribution over ordered levels and an expected score Urgency, quality, severity, review rubrics

A Choice is appropriate when exactly one option should be selected. A Noul is appropriate for a yes/no condition; multiple Noul questions can implement multi-label checks, though their probabilities need not sum to one. A Score is appropriate when the levels have a meaningful order, such as can wait < this week < today. vllm-sr

Example: customer support

Consider a customer who reports a damaged parcel and asks for a replacement today. Decision 1.0 illustrates three questions over the same state: vllm-sr

Type Ask the model Use the answer
Choice Which team should handle this: delivery, billing, or technical support? Route using the selected candidate ID and its distribution
Noul Does the customer request action today? Use the yes probability to decide whether to escalate
Score Rate urgency: can wait, this week, today Prioritize the queue using the level distribution and expected score

The important design point is that the application—not the model—owns the action policy. The model supplies probabilities; the application decides what probability threshold triggers escalation, refund approval, human review, or another workflow branch. vllm-sr

Candidate descriptions instead of fixed labels

A decision model does not need a fixed vocabulary of task labels. Candidates can be short identifiers such as billing or technical, or richer descriptions such as “Payments and refunds” and “Product faults.”

Decision 1.0’s Lux model uses a shared candidate readout: all candidates for one question are scored in a single forward pass, and candidate descriptions come from the request rather than a fixed label set. This makes the same model usable for routing, tool selection, policy checks, and evaluation without retraining the head for every new task. vllm-sr

Batch decisions

Real workflows rarely need one decision at a time. A support record may require a destination, refund check, escalation decision, and priority score. Applying those four questions to 128 records produces 512 decisions.

Decision 1.0’s Kai and Lex native Python API accepts up to 128 independent requests and 512 total decisions per local SDK batch submission, preserving request and question order. The runtime groups work into physical batches; the 512 figure describes submission capacity, not simultaneous forward passes or measured throughput. vllm-sr

Part 3: Model Architectures

Decision 1.0 family

Decision 1.0 is a family of six open-weight Decision Foundation Models released by the vLLM Semantic Router team. The family uses two architectural branches. vllm-sr

Model Built for Input budget
Decision-1.0-Kai-0.6B Compact general-purpose routing, conditions, and action selection 1,024 tokens
Decision-1.0-Lex-0.6B Operational decisions: customer service, invoices, security incidents, agent traces 1,024 tokens
Decision-1.0-Eos-0.8B Smallest hybrid decoder tier for longer evidence 16,384 tokens
Decision-1.0-Sol-2B Greater capacity for decisions over extended context 16,384 tokens
Decision-1.0-Nox-4B Combining conditions, applying rules, and choosing actions 16,384 tokens
Decision-1.0-Lux-9B Largest model and strongest overall result on the released decision suite 16,384 tokens

The input budget covers the complete state, question, and candidate descriptions. vllm-sr

Encoder branch: Kai and Lex

Kai and Lex use three bidirectional encoder paths built on Vela. Each path has separate interaction layers and readouts for Choice, Noul, and Score. vllm-sr

Conceptually:

             State + question + candidates
                           |
        +------------------+------------------+
        |                  |                  |
   Choice path        Noul path          Score path
        |                  |                  |
  candidate logits    yes probability   ordered level logits
        |                  |                  |
     distribution      probability       level distribution

This is a conceptual reconstruction of the three-path encoder design. Bidirectional encoders are naturally suited to classification because every token can attend to every other token in the input, which is useful when the answer depends on relationships across the whole state. vllm-sr

Decoder branch: Eos, Sol, Nox, and Lux

Eos, Sol, Nox, and Lux adapt Qwen3.5 text backbones. They combine Gated DeltaNet with full attention and use a shared candidate head. vllm-sr

This hybrid design reflects a common trade-off:

  • Full attention provides strong context modeling and is effective for long-range dependencies.
  • Gated DeltaNet is a more efficient sequence-mixing mechanism that can reduce the cost of processing long contexts.
  • A shared candidate head scores each supplied candidate, allowing the candidate set to vary per request.

Lux-9B scores all candidates for one question in a single forward pass; independent questions are processed in batches. vllm-sr

Part 4: AnyJev

What AnyJev does

AnyJev is an open-source framework that turns an LLM into a Jev-style decision model. It provides typed decisions and probability distributions without requiring generated text to be parsed. github

AnyJev provides two main paths:

  1. Training-free Decider: works with any open causal language model, with no training and no labels.
  2. Self-distilled Tacit: uses checkpoints trained through self-distillation so the model can answer in one forward pass. github

The problem with raw label logits

A naive way to build a decision model from an LLM is to prompt it with candidate labels and read the next-token logits for each label. This is simple but problematic:

  • The result can change when the order of options changes.
  • The model may have a prior preference for certain label strings.
  • The resulting probabilities may be poorly calibrated.

AnyJev’s L0 readout addresses both issues without labels by averaging position bias over rotations of the options and dividing out the label prior. github

L0 rotation readout

At level L0, AnyJev reads a K-option choice once per rotation of the options. Each rotation changes the ordering of candidates, and the readout aggregates the resulting distributions to reduce order sensitivity.

For each rotation r of the K candidate options:
    Read logits for each option label
    Convert logits to an option distribution

Aggregate distributions across rotations
Remove label prior
Return final calibrated decision distribution

This is a conceptual reconstruction of the rotation-based readout. The repository reports that, on Qwen3-8B for a 20-way BANKING77 task with 300 test items, L0 reduced answer flips when options were reversed from 0.230 to 0.073, improved accuracy from 0.747 to 0.803, and reduced expected calibration error from 0.240 to 0.184. github

The most consequential improvement is automation capacity: the share of decisions confident enough to automate at no more than 5% error rose from 7.7% with raw logits to 46.3% with L0, using no labels. github

Rotation budget

Running all K rotations is expensive for large candidate sets. AnyJev’s rotation budget reads only as many rotations as the decision needs.

The stopping threshold is calibrated against AnyJev’s own full-cycle answer, so it does not require labels. The repository reports that, at a certified 1% disagreement, it read 7.2 rotations instead of 18, yielding 2.2 times more decisions per second on vLLM and 2.3 to 2.7 times more on transformers, with accuracy unchanged. github

Tacit self-distilled models

Tacit models are trained by self-distillation: the model learns to produce, in one forward pass, the answers it would reach when it reasons. No human labels and no separate teacher model are involved. github

The trade-off is:

  • One-forward mode: fast and cheap; one prefill per decision.
  • Adaptive mode: low-confidence decisions are escalated to the model’s own reasoning, then read as a label distribution after the reasoning step.

Adaptive escalation is bounded by configuration:

Argument Default Meaning
adaptive False Send low-confidence decisions to the model’s own reasoning
tau 0.5 Low confidence when the log-probability gap between the top two options is below this value
max_cot_share 0.2 Maximum share of the recent decision window allowed to escalate
cot_window 1000 Number of recent decisions counted by the escalation cap
cot_max_tokens 8192 Reasoning budget for one escalated decision
engine "transformers" Also supports in-process vLLM or a remote vllm serve endpoint

The cap matters operationally: even if traffic becomes difficult, at most max_cot_share of the last cot_window decisions escalate. Every escalation is reported through route == "cot", and the first-pass result is retained. github

AnyJev code example

The following example is copied from the AnyJev repository and shows a Tacit decision over customer-service actions. github

from anyjev import Tacit

tacit = Tacit.from_pretrained("morriszjm/Tacit-9B")

d = tacit.decide(
    state="Customer: my package was due last Monday and it still has not arrived.",
    question="What does the customer want?",
    options=["track_order", "cancel_order", "refund", "change_address"],
)

d["answer"]   # selected option
d["probs"]    # {option: probability}
d["route"]    # "one_forward" or "cot"

Part 5: Calibration

Why calibration matters

A model can be accurate while still having unreliable probabilities. Calibration measures whether predicted confidence matches observed correctness.

For example, if a model assigns approximately 74% positive probability to many movie reviews, then roughly 74% of those reviews should actually be positive for the model to be well calibrated at that confidence level. magazine.sebastianraschka

This distinction is critical for decision systems because the application may use probability thresholds to automate actions:

  • Automatically route requests above 0.95 confidence.
  • Send 0.70 to 0.95 to a cheaper secondary check.
  • Escalate below 0.70 to a human or reasoning model.

An accurate but overconfident model will automate too many incorrect decisions. An underconfident model will escalate too much, increasing cost and latency.

Expected calibration error

Expected Calibration Error, or ECE, is a common calibration metric. Conceptually, it groups predictions by confidence bucket and compares average predicted confidence with observed accuracy in each bucket:

\[\mathrm{ECE} = \sum_b \frac{n_b}{N} \left| \mathrm{acc}(b) - \mathrm{conf}(b) \right|\]

where:

  • $b$ indexes confidence bins.
  • $n_b$ is the number of predictions in bin $b$.
  • $N$ is the total number of predictions.
  • $\mathrm{acc}(b)$ is observed accuracy in the bin.
  • $\mathrm{conf}(b)$ is average predicted confidence in the bin.

Lower ECE indicates better calibration. AnyJev reports ECE reduction from 0.240 with raw logits to 0.184 with L0 on its Qwen3-8B BANKING77 evaluation. github

Temperature scaling

Temperature scaling is a common post-hoc calibration method. It divides logits by a learned positive temperature $T$ before softmax:

$ p_i = \frac{\exp(z_i / T)}{\sum_j \exp(z_j / T)} $

where:

  • $z_i$ is the logit for candidate $i$.
  • $T$ is learned on a held-out calibration set.
  • $T > 1$ generally reduces confidence.
  • $0 < T < 1$ generally increases confidence.

Temperature scaling preserves the ordering of logits, so it changes confidence without changing the argmax decision. This general calibration background is added for clarity; it is not a claim about the internal training method of every decision model. magazine.sebastianraschka

Calibration in decision models

Decision models are designed around calibrated confidence. Jev’s documentation describes its probabilities as well calibrated, and the JEV-as-a-Judge paper uses the model’s confidence directly to decide whether to accept a verdict or escalate it to a reasoning judge. magazine.sebastianraschka

However, calibration is dataset- and distribution-dependent. A model calibrated on support-ticket routing may not be calibrated on medical triage, code review, or adversarial text. Production systems should validate thresholds on representative local data before relying on confidence-based automation. arxiv

Part 6: Decision Cascades

Accept or escalate

A decision cascade uses a fast decision model as the first stage and escalates uncertain or high-stakes cases to a slower reasoning system.

Input state
     |
     v
+----------------------+
| Decision model       |
| Returns probabilities|
+----------------------+
     |
     | confidence >= threshold
     |--------------------------------+
     |                                |
     v                                v
Accept decision              Escalate to System 2
                              - reasoning LLM
                              - human reviewer
                              - tool-using agent

This architecture is valuable when most decisions are easy but a minority require deeper reasoning. The fast model handles the bulk of traffic; the expensive path handles only uncertain cases.

JEV-as-a-Judge results

The JEV-as-a-Judge paper studies evaluation with JEV as a decision-only judge that returns label probabilities instead of text. Its confidence determines whether to accept the verdict or escalate to a reasoning judge. arxiv

Key reported findings:

  • Against 16 generative and reward-model judges, with blinded human adjudication, JEV came within three points of GPT-6 wherever a verdict could be read from the text.
  • It did so at 0.36% of GPT-6’s fee and with a 0.15-second median latency.
  • It fell behind where the verdict had to be derived, such as math, code, and logic.
  • With a threshold frozen in advance, accepting confident verdicts and escalating the rest was 0.9 points more accurate than GPT-6 on 1,610 held-out pairs, at 41% of GPT-6’s fee.
  • In a pre-specified live test on two new workloads, the cascade matched GPT-6’s accuracy exactly.
  • Confidence routing weakened on style-adversarial pairs and reference-free prose. arxiv

The practical lesson is that a decision model is strongest when the judgment can be read from the supplied evidence. It is weaker when the correct answer requires deriving a new result through multi-step reasoning.

Part 7: Search and Agent Applications

SearchJev

SearchJev is a fast, calibrated System-1 model for search agents. It separates search decisions from System-2 reasoning and generation. arxiv

Given a search state and a decision schema, SearchJev directly scores legal options without autoregressive output generation. It uses Soft-Label Learning for Calibrated Decisions, or SLCD, to learn decision probabilities from uncertain supervision and calibrate confidence. arxiv

SearchDecision-Bench unifies six types of search decisions for training and evaluation. The paper reports:

  • SearchJev improves decision quality over same-size Qwen3.5 autoregressive models.
  • It achieves 5.2 to 5.3 times faster decisions.
  • It reduces average expected calibration error by 41% to 74%.
  • In dual-system agents on BrowseComp-Plus, active search time improves by 3.7 to 4.7 times.
  • Answer accuracy improves from 45% to up to 54%. arxiv

Search-agent decision examples

Typical System-1 decisions in a search agent include:

Decision Candidate options Use of result
Relevance Relevant, not relevant Filter or retain a document
Evidence sufficiency Sufficient, insufficient Stop searching or continue
Next action Search, read, refine query, answer Control the agent loop
Query quality Good, needs refinement Decide whether to regenerate a query

These examples illustrate the decision types described by SearchJev; the exact benchmark schema contains six decision types, and the paper should be consulted for the complete task definitions. arxiv

Agent policy and routing

In an agent system, decision models can gate actions before execution:

Agent observes state
        |
        v
Decision model
        |
        +-- safe_action probability high --> execute tool
        |
        +-- uncertain or unsafe -----------> ask planner / human
        |
        +-- policy violation --------------> block action

The decision layer is especially useful for:

  • Selecting a tool or backend.
  • Checking whether an action is allowed by policy.
  • Deciding whether retrieved evidence supports an answer.
  • Triage of incidents, tickets, invoices, or agent traces.
  • Scoring completed agent runs against a rubric. vllm-sr

Part 8: Building and Fine-Tuning

When to fine-tune

A general decision model is attractive when tasks change frequently or labeled data is scarce. A specialized classifier can still be better when:

  • The task is narrow and stable.
  • Latency requirements are extreme.
  • The label set is fixed.
  • Large volumes of high-quality labeled data exist.
  • The cost of maintaining a custom model is acceptable.

Sebastian Raschka’s analysis frames the trade-off clearly: Jev-like models are more general than task-specific classifiers, while specialized classifiers can be better, faster, and cheaper for a narrow, well-defined problem. magazine.sebastianraschka

SFT workflow

Supervised fine-tuning, or SFT, adapts a decision model to domain-specific states, questions, candidates, and preferred decisions. The Liquid4All cookbook provides SFT notebooks for decision models using both Unsloth and TRL. vllm-sr

A typical workflow is:

1. Define decision schema
   - state fields
   - questions
   - candidate sets
   - score rubrics

2. Collect or synthesize examples
   - state
   - question
   - correct option or score level

3. Format for SFT
   - preserve candidate order policy
   - include candidate descriptions
   - retain task instructions

4. Fine-tune
   - train model and decision head
   - use validation split for calibration

5. Evaluate
   - accuracy
   - calibration error
   - escalation rate
   - latency and cost

6. Deploy
   - serve with vLLM, llama.cpp, or managed endpoint
   - monitor drift and threshold performance

This workflow is a general engineering reconstruction; the exact data format and training hyperparameters depend on the chosen framework and base model.

Unsloth and TRL

Unsloth provides documentation and tooling for training your own decision model, and the Liquid4All cookbook includes notebooks for SFT with both Unsloth and TRL. vllm-sr

Tool Role
Unsloth Efficient fine-tuning library and decision-model training guide
TRL Transformer Reinforcement Learning library for training workflows
Hugging Face Model and dataset hosting
vLLM High-throughput serving
llama.cpp Local CPU/GPU inference for supported model formats

These are infrastructure options; selecting one does not by itself guarantee calibration or accuracy. Evaluation on task-specific held-out data remains necessary.

Part 9: Deployment

Local inference

Decision 1.0 provides weights and local inference code in its model repositories. An HTTP endpoint must be deployed separately if the application uses the System One-compatible HTTP interface. vllm-sr

AnyJev supports several execution modes:

Mode Description
transformers In-process Hugging Face Transformers execution
vllm vLLM running in the same process
server Client to a separately running vllm serve endpoint
HTTP gateway AnyJev endpoint in front of an upstream model server

The AnyJev HTTP gateway listens on 127.0.0.1 and has no authentication of its own, so it should not be exposed directly to untrusted networks without adding authentication and transport security. github

System One request format

Decision 1.0 uses the upstream System One request format: state, model, and named questions. The official TypeSafe Python SDK or an equivalent HTTP request can be used with a SystemOne-compatible deployment. vllm-sr

Install the SDK:

pip install typesafe-sdk

The following Python example is published in the Lux model card and reproduced from the Decision 1.0 announcement. vllm-sr

from typesafe_sdk import Choice, Noul, TypeSafeClient

with TypeSafeClient(
    api_key="YOUR_ENDPOINT_API_KEY",
    base_url="https://your-decision-endpoint.example",
    model="Decision-1.0-Lux-9B",
) as client:
    result = client.system_one(
        state="Customer reports a duplicate charge and asks for a refund.",
        questions={
            "route": Choice(
                instructions="Which team should handle this request?",
                criteria={
                    "billing": "Payments and refunds",
                    "technical": "Product faults",
                },
            ),
            "refund_requested": Noul(
                instructions="Did the customer request a refund?"
            ),
        },
    )

print(result.choices["route"].choice)
print(result.nouls["refund_requested"].noul)

Deployment checklist

  • Define explicit candidate descriptions rather than relying only on short labels.
  • Set action thresholds from local validation data, not intuition.
  • Log the full probability distribution, not only the selected option.
  • Monitor calibration, escalation rate, latency, cost, and drift.
  • Bound reasoning escalation with a token budget and a share cap.
  • Keep a human or System-2 path for high-impact or low-confidence decisions.
  • Test candidate-order sensitivity, especially when using raw logits.
  • Validate behavior under adversarial, out-of-distribution, and reference-free inputs. github

Tacit one-forward Very low Low Strong when model is well trained High-volume operational decisions
Adaptive reasoning escalation Variable Higher Better on uncertain cases High-stakes or ambiguous decisions
Full System-2 reasoning Highest Highest Strongest for derivation-heavy tasks Planning, math, code, complex logic

AnyJev’s adaptive mode operationalizes this trade-off by sending only a capped share of low-confidence decisions to reasoning. github

Part 11: Limitations and Open Questions

Known limitations

  • Derived answers are harder. JEV-as-a-Judge found that decision-only judging falls behind where the verdict must be derived, such as math, code, and logic. arxiv
  • Adversarial and reference-free evaluation are difficult. Confidence routing weakened on style-adversarial pairs and reference-free prose. arxiv
  • Calibration is not universal. A model calibrated on one distribution may be miscalibrated on another; local threshold validation is necessary. arxiv
  • Candidate order can matter. Raw label logits can flip answers when options are reordered; AnyJev’s L0 reduces but does not inherently eliminate the need for careful evaluation. github
  • Escalation costs tokens. AnyJev reports hundreds of additional generated tokens per escalated decision for Tacit-9B and Tacit-4B. github
  • Benchmark scores are suite-dependent. Decision 1.0’s results use a selected 54-task suite and a weighted overall metric; they should not be generalized as universal superiority. vllm-sr
  • Open questions remain. AnyJev’s roadmap lists label-free early exit, agent-loop evaluation, additional log-prob backends, and span readout beyond 26 options as areas still under development. github

Evaluation gaps

Production adoption should evaluate more than headline accuracy:

  • Accuracy by decision type and candidate-set size.
  • ECE and reliability diagrams.
  • Automation rate at a fixed error budget.
  • Escalation rate and reasoning-token cost.
  • Sensitivity to candidate order and paraphrasing.
  • Out-of-distribution performance.
  • Latency distributions, including median and p95.
  • Failure impact by action severity.

Final Technical Takeaways

  • Central mechanism: Decision models map a state, question, and candidate set to typed probability distributions instead of generating free-form answers. vllm-sr
  • Main architectural insight: Separate frequent System-1 decisions from slower System-2 reasoning; use the fast path for routing, gating, and scoring, and escalate uncertainty. arxiv
  • Important specifications: Decision 1.0 includes six open models from 0.6B to 9B parameters, with input budgets of 1,024 or 16,384 tokens; Lux-9B reports an overall score of 76.94 on the release’s 54-task suite. vllm-sr
  • Key calibration result: AnyJev’s label-free L0 readout raised the share of Qwen3-8B BANKING77 decisions automatable at no more than 5% error from 7.7% to 46.3%. github
  • Most important trade-off: One-pass decision readouts minimize latency and cost, while reasoning escalation improves difficult cases at materially higher token cost. github
  • Main limitation: Decision models are strongest when the answer can be read from supplied evidence; derivation-heavy tasks such as math, code, and logic still benefit from System-2 reasoning. arxiv
  • Engineering implication: Treat the decision layer as a programmable control plane: define candidates and rubrics explicitly, use calibrated probabilities for policy, and reserve expensive reasoning for genuinely uncertain or high-impact cases. vllm-sr
